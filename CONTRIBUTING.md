# Contribuir

1. Crea una rama por cambio.
2. Mantén `SKILL.md` enfocado; mueve detalle especializado a `references/`.
3. Actualiza esquemas, ejemplos y evals cuando cambie el contrato.
4. Ejecuta `npm test` antes de proponer el cambio.
5. No agregues secretos, IDs privados, datos personales ni material sin licencia.
6. Explica en el pull request qué proveedor o flujo se probó y qué fallback conserva la portabilidad.

Los cambios de proveedor deben describir capacidades observables y fecha de verificación, no promesas permanentes del producto.
